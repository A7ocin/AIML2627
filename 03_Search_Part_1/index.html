Search · 02 · Explain the algorithm in words

Search in five steps

Use the waiting list to explore one candidate at a time.

StepWhat to do
1 · InitializePut only the start path ⟨A⟩ in the frontier.
2 · SelectChoose and remove one waiting path.
3 · TestIf its endpoint is a goal, return this path as the solution.
4 · ExpandOtherwise, extend the path to each legal successor.
Add these extended paths to the frontier.
5 · RepeatRepeat steps 2–4. If the frontier is empty, return failure.

Step 2 defines the search strategy: choosing a different waiting path changes the order of exploration.

Handout explanation ↗See the pseudocode nextLink to this slide
Follow the five numbered steps in the handout. Initialization happens once; steps 2–4 form the loop. A candidate is a whole path, so a successful search can return the route, not merely the goal state. Test the selected path’s endpoint before expanding it: reaching a goal ends the search immediately. If there is no goal, create one extended path for each legal successor. Check that the frontier is nonempty before selecting again. Failure means that no candidates remain under this search policy; an infinite search can continue without returning either success or failure. Connect selection to later strategies: oldest path for breadth-first, newest for depth-first, and lowest accumulated cost for lowest-cost-first. This is the generic path-search skeleton; cycle and duplicate policies determine which extensions a concrete implementation keeps. Ask students which steps happen only once and which steps repeat.
Search · Read the mathematics

Turn the five steps into a mathematical loop

Input: graph G, with vertices V and edges E; start vertex vₛ and goal vertex vG. Output: a path, or failure.

F ← {⟨vₛ⟩}
while F ≠ ∅:
    p ← select(F)
    F ← F ∖ {p}
    if end(p) = vG: return p
    F ← F ∪ {p ⊕ v : (end(p), v) ∈ E}
return failure

Name the variables

F: frontier of waiting paths
p: the path selected from F
v: a legal next vertex after p
select(F): choose a path using the strategy
end(p): the last vertex of p

Read the operations

←: assign · ∅: empty collection
∖ {p}: remove p · ∪: add candidates
p ⊕ v: append vertex v to path p
∈: belongs to; (end(p), v) ∈ E requires a legal edge to v.

Test the selected endpoint before extending it. The selection rule changes; the path and goal definitions stay the same.

Handout explanation ↗Link to this slide

The original handout uses lowercase f for the frontier; we use uppercase F to distinguish it from A* score f. This skeleton searches paths; cyclic graphs require a suitable cycle/duplicate policy.

Iterative deepening (IDS): keep the stack, limit the depth

Limit 0Limit 1Limit 2…
  • Run depth-limited DFS from the root, using a stack or recursion.
  • If a deeper branch was cut off, increase the limit.
  • Restart the search; stop at the first goal.
Shallowest solution, small frontier
  • Complete for finite branching and a finite-depth goal.
  • Fewest edges; cost-optimal for equal positive edge costs.
  • b is the maximum children per node; d is the shallowest goal depth in edges.
  • O(bd) bounds record-count growth by a constant times b × d; the price is repeated work.

02 · Uninformed search

Repeated work can be a reasonable price

We count node visits (search work), not edge costs. Assume every pass runs in full.

1 + 10 + 100 + 1000 = 1111

These are the nodes at depths 0, 1, 2 and 3. One full traversal visits each node once.

1·4 + 3·10 + 2·100 + 1000 = 1234

IDS restarts at limits 0, 1, 2 and 3: the root is visited 4 times, depth 1 3 times, depth 2 twice, and depth 3 once.

A complete tree · b = 10, d = 3

b = children per non-leaf node;
d = maximum depth in edges.

One pass through depth 3:
1111 node visits

Deepening through limits 0–3:
1234 node visits

123 extra visits: about 11% more work.

Most nodes are at the deepest level, which IDS visits only once. A long single chain is a less favorable case.

The two sums count search effort, not the solution’s accumulated edge cost g or the number of nodes simultaneously held in memory. Use a full tree with branching factor 10, counting all visits within each limit and assuming no early goal stop. In the first sum each level contributes its node count once. In the second sum each level’s count is multiplied by the number of passes that reach it: 4×1, 3×10, 2×100 and 1×1000. The extra-work percentage is (1234−1111)/1111, about 11.1%. The benefit is depth-first-sized storage rather than retaining BFS’s broad frontier. This percentage belongs to the example; for full trees with fixed b greater than 1, the visit-count ratio approaches b/(b−1) with increasing depth. A chain has much greater relative repetition. Transition: we have counted the work of searching; next consider the cost of the solution itself.

Search · Will the algorithm reach the goal?

Why a reachable goal can keep waiting

Uniform-cost search (UCS) selects the cheapest waiting path—even when a goal is already in the frontier.

The goal keeps losing the comparison

After expandingWaiting paths · total cost
AA → B: 0   |   A → Goal: 1
BA → B → C: 0   |   A → Goal: 1
CA → B → C → D: 0   |   A → Goal: 1

Every selected free path creates another free path. The goal is never selected.

Finite graph: avoid repeating states

With nonnegative costs, keep a new route to a state only if it improves the best known cost. Zero-cost loops then stop adding copies.

Infinite space: make every step count

Require finitely many next moves per state and one fixed positive lower bound ε > 0 on every step cost; ε (epsilon) names that bound. For example, if each step costs at least 1, detours cost at least 1, 2, 3, …

With these safeguards, only finitely many candidates can come before the goal. UCS eventually selects it.

Handout explanation ↗Link to this slide
First ask which waiting path UCS chooses: total cost zero or total cost one? Repeat after B and C to show why the goal keeps waiting. The chain has infinitely many distinct states, so this is not a duplicate-state bug. The conditions in the lower cards are two separate sufficient settings, not conditions that must all hold at once. On a finite graph, nonnegative edge costs plus best-cost duplicate handling and skipping obsolete queue entries ensure termination. In an infinite space, finite branching, a finite-cost reachable goal, and one fixed positive lower bound epsilon for every edge imply finitely many paths with cost at most the goal's cost; this also handles ties. Merely saying each edge is positive is insufficient if the costs shrink toward zero. The example in the diagram violates the positive-lower-bound condition. Goal testing is still on selection, as taught earlier. These are conditions for eventually reaching a goal, distinct from the argument that a selected goal is cheapest.
