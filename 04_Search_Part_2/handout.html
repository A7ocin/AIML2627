Reconnect before continuing

Welcome to informed search. In Part 1 we built a complete toolkit of uninformed strategies — breadth-first, depth-first, iterative deepening and lowest-cost-first. Those methods are systematic but blind: they explore according to mechanical rules (oldest, newest, shallowest, cheapest-so-far) with no sense of where the goal actually is.

This part adds a crucial new ingredient: an estimate of how far each state still is from the goal. With that extra signal, search can stop wandering blindly and instead steer toward promising regions — often finding solutions much faster. The overall aim of this lecture:

  • Use these estimates (called heuristics) to guide exploration;
  • Then carefully examine when the resulting guided searches are complete or guaranteed to find a cheapest route.

Before you begin, make sure you can still answer three recap questions from Part 1:

  • Represent a task using states, actions, a goal and costs. A state holds everything needed to decide the next move; legal transitions are edges (possibly with costs); a solution path ends at a goal; many strategies return on selection, while branch-and-bound saves the solution and continues; and cumulative cost measures path quality.
  • Explain the difference between queue and stack exploration. A queue (first-in-first-out) selects the oldest waiting path, giving breadth-first behavior; a stack (last-in-first-out) selects the newest, diving deep — and this choice of data structure determines both exploration order and memory use.
  • Choose an uninformed method using the costs and memory available. Fewest steps cheaply in memory → iterative deepening; minimum weighted cost → lowest-cost-first with nonnegative edges, sound duplicate handling and termination conditions; any solution with a small frontier → depth-first, while accounting for cycles, infinite branches and ordering.

With those foundations fresh, you are ready to see how a simple estimate transforms search from blind to guided.

The sequence is: build a useful estimate, compare global and local selection rules, combine past and future cost in A*, check the guarantee assumptions, then use lower bounds to prune depth-first search. The Part 2 labs use the supplied edge weights for returned solution costs. Their course-tree goal is S; the Part 1 BFS/DFS exercises are explicitly linked from the practice section.

Chapter 2 / 22Give the search a useful estimate

The single new idea that turns uninformed search into informed search is a quantity called a heuristic, conventionally written h(n). Here n stands for any state, and h(n) is defined as:

h(n) = an estimate of the cost still required to reach a goal from state n

Think of it as a rough guess, attached to every state you encounter, answering: “about how much more effort will it take to finish from here?” For example:

  • In route-finding on a map, h could be the straight-line distance from this city to the destination — a reasonable guess that never overestimates the real road distance.
  • In a sliding-tile puzzle, h might count how many tiles are out of place, or sum each tile’s movement needed to reach home — both cheap estimates of remaining difficulty.

It is essential to understand what a heuristic does and does not do:

  • It does not replace the frontier or the successor function. We still keep our collection of candidate paths, and we still generate successors exactly as before. The graph machinery from Part 1 remains fully intact.
  • It supplies an additional signal: one more number per state that helps us choose which unfinished route to investigate next — a guide for the frontier’s selection step.
informed = uninformed machinery + a heuristic guiding which path to expand first

Why is this worth doing? Because a good heuristic acts like a compass needle pointing toward relevant regions of the search space. Instead of expanding candidates purely by age or depth, we can prefer paths that seem close to finishing — reaching the goal with far less exploration.

The key practical constraint on any useful heuristic: it must be cheap to compute. If computing h(n) were as expensive as solving the whole problem from n onward, that computation could erase the search-time benefit. The value of a heuristic is precisely that it gives you a good directional signal for much less effort than actually solving the task — which is what makes “guided” search both faster and still affordable.

h(n) ≈ remaining cost from n to a goal

From a vertex weight to a heuristic function

hvG : V → ℝ,   v ↦ estimated remaining cost from v to vG
G = (V, E, ωV, ωE),   ωV = h

The goal is fixed when defining this function, so we usually shorten hvG(v) to h(v). Vertex weights ωV hold estimates; edge weights ωE hold actual transition costs. When only vertex weights matter, the original writes G = (V, E, ωV). A* uses both. With unweighted edges, take ωE(u, v) = 1 for every (u, v) ∈ E, so accumulated cost counts transitions.

For a destination at coordinates (xG, yG) and a vertex at (x, y), Euclidean distance is h(v) = √((x − xG)² + (y − yG)²). This is straight-line distance, not the actual road distance; the lower-bound interpretation requires distance costs in compatible units. With multiple valid destinations, use the distance to the nearest one.

Not every guess makes a good heuristic — there are two important properties that separate useful estimates from misleading ones. The first is about units and meaning: a heuristic must refer to the same objective and use the same units as the cost it is estimating.

h(n) estimates remaining cost in the SAME currency as edge costs (distance, time, price…)

Consider route-finding. Straight-line (“as-the-crow-flies”) distance is a fine lower bound on road distance — roads can never be shorter than the direct line between two points. But that same number would not automatically lower-bound travel time: you might drive 10 km in minutes or hours depending on traffic, so straight-line kilometres say nothing safe about minutes without extra assumptions (e.g., a known speed). A heuristic is only trustworthy when its units and objective match what it claims to bound.

The second idea gives us a systematic way to build useful heuristics: relaxing constraints. If you take your hard problem and remove some of its restrictions, you get an easier problem that can be solved cheaply. Its solution value is then very often a valid bound on the original harder problem.

  • The classic example is a puzzle like the sliding-tiles: to estimate remaining moves in the real (constrained) game, solve the relaxed version where tiles may pass through each other — that easier computation gives a lower bound on the true number of moves needed. In route-finding, ignoring obstacles yields straight-line distance as the relaxed problem’s solution.
  • The principle is general: an optimum of a relaxation bounds the original below because removing restrictions can only make things cheaper or equal, never more expensive.
relaxed (easier) problem solved cheaply → its value lower-bounds the hard problem

Finally, why does all this effort to build good, safe estimates pay off? Because of a direct relationship between heuristic quality and search efficiency: the more informative a safe (admissible) estimate becomes — that is, the closer it gets to the true remaining cost without ever overestimating — the more irrelevant exploration it can prevent.

  • A crude bound like “0” tells us nothing and helps not at all; a tighter safe bound can make fewer paths competitive, although ties, evaluation cost and graph-state reopening still matter. The whole art of informed search lies in crafting estimates that are safe yet tight enough to prune away dead ends early.

Chapter 4 / 22Greedy best-first: follow the smallest estimate

The mathematical selection rule

p ← arg minq ∈ F h(end(q))

F is the entire frontier, q ranges over its candidate paths, and end(q) is the candidate’s last vertex. arg min chooses a path whose endpoint estimate is smallest; it does not return the score itself. Ties need a fixed rule. In the course tree, A is followed by B and E; after E is expanded, F has the lowest available estimate, h(F) = 2. Greedy can therefore switch branches without finishing E’s descendants. Its priority ignores the cost already spent.

The first informed strategy is delightfully simple — so simple it earns the name greedy best-first search. Its rule:

across the whole frontier, select next the path whose endpoint has the smallest heuristic h(n)
  • “Greedy” means it makes the most attractive choice according to h at the current step: whichever candidate looks closest to a goal right now.
  • It compares every state sitting on the frontier and picks the one with the lowest remaining-distance estimate — regardless of how old it is or what depth it lies at.

The critical detail, which you must notice: greedy best-first ignores entirely the cost already spent to reach that endpoint. It judges a candidate solely on its future promise (h), not on its past expense. Compare this with lowest-cost-first from Part 1, which used only the past (g) and ignored the future; greedy uses only the future and ignores the past.

lowest-cost-first: pick smallest g (past cost)  ·  greedy best-first: pick smallest h (future estimate)

What does this buy us? Speed of discovery. Because greedy lunges toward whatever seems nearest to a goal, it often finds a solution very quickly — racing down promising corridors without wasting time on unpromising ones.

But there is no free lunch: greedy best-first provides no general minimum-cost guarantee. It can deliver you an expensive route while a cheaper one existed. The failure mode is easy to picture:

  • A state might look excellent in terms of remaining distance (small h) only after you have already made a very costly detour (large g). Greedy never notices the accumulated bill, so it happily finishes down that expensive path.
looks close now + huge cost already paid → greedy may return an overpriced route

So treat greedy best-first as a fast heuristic-driven explorer: potentially useful for finding a solution quickly, but without a general speed or minimum-cost guarantee. That goal requires balancing both past and future — which is exactly what A*, later in this lecture, will do.

In the selection rule, F is the frontier, q a waiting path, end(q) its endpoint, and p the selected path. h(end(q)) estimates remaining cost; arg min returns a minimizing path and ← assigns it. Greedy ignores g, the path cost already paid.

The counterexample has A → B → G costing 1 + 9 = 10, and A → C → G costing 4 + 1 = 5. With h(B) = 0, h(C) = 1 and h(G) = 0, greedy selects B and then G. Both estimates are admissible, yet greedy returns the more expensive solution: admissibility alone does not make its h-only selection optimal. Like DFS, greedy can also fail to reach a goal on an infinite space; it does not guarantee a fast answer.

select p with minimum h(end(p))

Chapter 5 / 22Greedy best-first · use h alone

The interactive example for greedy best-first search rewards careful prediction, and it contains a behavior that often surprises students at first. Here is how to study it:

  1. Before advancing each step, scan all the h values currently displayed on the frontier.
  2. Predict which endpoint has the smallest h — that is the next path greedy will select.
  3. Advance and check whether you were right.

In this course tree, after A → B → E the new children have h(K) = 8 and h(L) = 7, while the older path to F has h(F) = 2. Greedy selects F next. The other waiting endpoints G, C and D have estimates 9, 4 and 3; none beats F.

if h(F) < all of E's children → greedy leaves E and goes to F next

Why is this allowed? Because greedy best-first makes its priority comparison globally across the entire frontier, not locally within one branch. Every waiting path competes on equal terms, judged purely by h. There is no obligation to finish exploring E’s descendants just because we started them; if some other state anywhere looks closer to a goal, greedy jumps to it.

  • This global-jumping behavior is what distinguishes greedy best-first from a depth-first method that merely sorts its newly generated siblings. Depth-first commits to the branch it chose and follows it down; it never re-competes against distant states. Greedy, by contrast, keeps reconsidering everything at every step.

Explain the actual jump using the displayed values: “F has h = 2, less than K’s 8 and L’s 7, so greedy selects the older route to F.” With default goal S, this weighted lab returns A → B → F → P → S at cost 12.

Chapter 6 / 22Heuristic DFS: order siblings, then go deep

p₁, …, pₘ are the m new path extensions of the selected route; i indexes those paths, and end(pᵢ) is path i’s last state. This m counts new children, rather than maximum search depth. The function h estimates remaining cost at each endpoint. The LIFO stack retains older alternatives underneath the newly pushed children.

The ordering rule and the stack

h(end(p₁)) ≥ h(end(p₂)) ≥ … ≥ h(end(pₘ))
push p₁, p₂, …, pₘ; then pop pₘ

These are only the new extensions of the selected path. Push the largest estimate first and the smallest last so the best-looking new child sits on top of the LIFO stack. Equivalently, sort by ascending −h. At A, the estimates are h(C) = 4, h(D) = 3 and h(B) = 2: push ⟨A, C⟩, ⟨A, D⟩, ⟨A, B⟩, then pop the route to B. Older alternatives remain underneath. This is local ordering, unlike greedy’s comparison over the full frontier.

Heuristic depth-first search takes a gentler approach than greedy best-first: it uses the heuristic locally, to decide which newly generated children to try first, but otherwise keeps ordinary depth-first behavior. This hybrid is worth understanding carefully because it behaves very differently from global-greedy.

  • When we expand a state and generate its successors, we push children with larger heuristic values first and the most promising child (smallest h) last, so it ends up on top of the stack.
  • Then we continue exactly as plain DFS: always dive into the newest candidate and follow that branch down.
local: order each node's own children by h · global structure: ordinary depth-first stack

The key contrast with greedy best-first is where the heuristic applies:

  • Greedy best-first makes every selection a global competition among all frontier endpoints, re-ranking everything at each step.
  • Heuristic DFS uses h only to pick which child of the current node looks best; afterwards it commits deeply, exactly like depth-first. It can choose a promising sibling first without turning every later choice into another global contest.

What are the consequences? Because heuristic DFS keeps the stack-based structure:

  • It retains memory advantages of DFS: only one deep branch plus a few waiting alternatives, not an entire frontier layer — far cheaper than greedy’s global bookkeeping or BFS.
  • And it inherits depth-first limitations too: no optimality guarantee, and sensitivity to ordering. The heuristic helps pick good branches first but cannot protect against every bad case.

In the running tree, E generates K (h = 8) and L (h = 7). Push K first and L last, so L is on top. Heuristic DFS then selects L and K before returning to the older F (h = 2), even though F has the smallest estimate among those three paths. That is local ordering followed by depth-first commitment.

commit deep now → may ignore a good waiting alternative until this subtree ends

So heuristic DFS offers a useful middle ground: the direction of depth-first (lean memory, fast commitment) plus local guidance to try promising children first — while accepting that once committed, it stays put.

The small-frontier comparison assumes compact parent-linked records and bounded branching; storage still grows with explored depth. A global visited set or the widget’s stored rewind frames adds memory. Heuristic DFS inherits the possibility of being delayed forever by an infinite branch, as well as DFS’s lack of a general optimum guarantee.

best new child goes on top

Chapter 7 / 22Heuristic DFS · local priority, deep commitment

This interactive example directly contrasts heuristic DFS with greedy best-first, and it drives home one of the most important conceptual lessons in this entire lecture — so study the sequence carefully.

  • Watch what happens after we enter state E. In the greedy example from a moment ago, F’s small heuristic could pull greedy away to explore F even while E still had unexpanded children.
  • In this heuristic DFS example, something different happens: even if F has a better estimate than some of E’s descendants, heuristic DFS will keep pushing through those descendants. Why? Because once we expanded E and pushed its children onto the stack, they occupy the top. Depth-first discipline says “take from the top” — so down we go into them, regardless of whether F elsewhere looks more promising.
heuristic DFS: descendants sit on top → explored before the better-looking F lower in the stack

The general lesson hiding here is profound and easy to miss:

using a heuristic does NOT uniquely define an algorithm

Both greedy best-first and heuristic DFS “use h.” Yet they behave completely differently — one re-ranks everything globally, the other orders only local children then commits deep. The estimate is not the whole story:

  • Where the estimate enters the selection process matters as much as (sometimes more than) the estimate itself.
  • The same numbers can produce radically different exploration depending on whether h drives global re-ranking, local sibling ordering, or some other insertion into the loop.

This is why you should describe a search strategy by both what signal it uses and how that signal controls selection. Two algorithms can share an identical heuristic yet be entirely different methods. When you study A* next, notice again exactly where g and h enter the priority — because getting that placement right is precisely what gives A* its powerful guarantees.

Chapter 8 / 22A*: combine the cost paid and the cost ahead

p is a path, q a waiting candidate, F the frontier and end(p) its last state. g(p) is actual cost from the start; h(end(p)) estimates what remains; f(p) is their sum. State labels such as F in A → B → F refer to a graph vertex; the frontier F is a separate mathematical variable.

The score and selection formula

f(p) = g(p) + h(end(p))
p ← arg minq ∈ F f(q)

F is the frontier. For each waiting route q, add its actual accumulated cost g(q) to the estimated cost still ahead h(end(q)); select a path with the smallest resulting f(q).

The start path has g(⟨A⟩) = 0 and f(⟨A⟩) = 0 + 5 = 5. Its extensions score 1 + 2 = 3 via B, 2 + 4 = 6 via C and 4 + 3 = 7 via D. After selecting B, the new routes score 3 + 1 = 4 via E, 7 + 2 = 9 via F and 4 + 9 = 13 via G. The routes to C and D still compete, so E is selected next.

A* (pronounced “A star”) is the most famous informed-search algorithm — and for good reason: it carefully balances the two pieces of information we have been keeping apart, past cost and future estimate.

  • g(p): the known, exact cost already paid along this path p from start to its endpoint. This is certain fact, not a guess.
  • h(n): the heuristic estimating how much more it will take from that endpoint to reach a goal — our best (imperfect) forecast of what remains.

A* combines them by simple addition into a single score f(p):

f(p) = g(p) + h(endpoint of p)
selection rule: always select the frontier path with the smallest f; test for a goal before expanding it

What does f represent? It is an estimate of the total cost to complete this route all the way from start to goal through this particular path: everything already spent (g) plus a forecast of what remains (h). By choosing the smallest f, A* simultaneously rewards paths that have made good progress cheaply and avoids abandoning ones that still look close — it weighs progress already made against the remaining task.

  • Notice how this places A* between our earlier methods: lowest-cost-first used only g (past), greedy best-first used only h (future); A* uses both. That balanced perspective is what makes it so effective.

A useful sanity check to confirm you understand the formula: if we set h identically zero, then f = g + 0 = g, and A* reduces exactly to uniform-cost (lowest-cost-first) search. In other words, lowest-cost-first is just A* with a completely uninformative heuristic — which tells you that A*’s extra power comes precisely from the guidance of h.

h ≡ 0 → A* = uniform-cost search

With an admissible heuristic, nonnegative costs, goal testing on selection and a search policy that preserves cheaper routes, A* returns a minimum-cost solution when it selects a goal. The finite-branching and fixed positive minimum-edge-cost conditions later in the lecture provide a sufficient termination setting for a finite-cost reachable goal. In graph search, admissibility alone does not justify discarding improved routes to expanded states. Heuristic guidance can reduce exploration; runtime also depends on evaluating h, ties and reopening.

Chapter 9 / 22The first A* decision

The first comparison in the course tree makes the arithmetic explicit. A–B has g=1 and h=2, hence f=3; A–C has f=6; and A–D has f=7. A* therefore selects B. Chapter 11 / 22Admissible means “never overestimate”

Two properties of the heuristic

The heuristic h estimates the cheapest remaining cost, using zero at a goal. Admissibility asks whether that estimate ever exceeds the true cheapest cost still needed. An underestimate is allowed: if 6 remains, h = 4 is safe but h = 8 is too high. This supports A*’s optimality when better routes remain available and goals are tested on minimum-score selection.

Consistency asks whether estimates agree across each move: the decrease in h must be no greater than the move cost. For a move costing 1, a change from 3 to 2 passes, while a change from 5 to 2 fails. This is a stronger property. With zero estimates at goals, a consistent heuristic is also admissible; an admissible heuristic can still be inconsistent. With correct cost updates, consistency lets graph A* avoid reopening expanded states. With an admissible but inconsistent heuristic, graph A* may need to reopen a state when a cheaper route is found. These heuristic properties are distinct from the algorithm’s rules for selecting paths, testing goals and preserving cheaper routes.

We said A* guarantees an optimal solution “under suitable assumptions.” The most important of those assumptions is that the heuristic be admissible. This is a precise mathematical condition, and understanding it fully tells you exactly why A* can trust its own choices.

0 ≤ h(n) ≤ h*(n), where h*(n) is the true least remaining cost  ·  (and h(goal) = 0)
  • “Never overestimate”: an admissible heuristic’s value is always less than or equal to the real minimum cost still needed. It may guess too low, but it never guesses too high.
  • Zero at a goal: when you are already at a goal, no more work remains, so h must be 0 there (the nonnegative estimate cannot exceed the zero remaining cost).

The straight-line-distance example fits perfectly: real roads can never be shorter than the direct line between two points, so straight-line distance is an admissible lower bound on road travel. A heuristic that could overestimate — say, guessing 10 when the true remaining cost is only 4 — would break A*’s reasoning by making a good path look artificially expensive.

A numerical example: suppose the true cheapest remaining cost from a state is 6. An estimate of 4 is a safe underestimate; 6 is exact and also safe; 8 overestimates and is not admissible at this state. The condition must hold at every state, so one successful example cannot establish admissibility of the whole heuristic. If a path has already paid g = 3 and uses h = 4, its total estimate is f = 3 + 4 = 7. The cheapest completion through that path costs 3 + 6 = 9. Thus f is a lower bound: it cannot exceed the cost of any completed solution extending this path.

Why does admissibility matter so much? Because of this chain of reasoning:

if h never overestimates → f = g + h is a LOWER BOUND on the total cost of any completed solution through this path
  • Let C be the cost of the selected goal. At a goal, h = 0, so f = g = C. If a cheaper solution of cost C* still existed, a waiting prefix of that solution would have f ≤ C* < C and would have been selected first. This requires that the search has not incorrectly discarded that cheaper prefix. Tree search preserves it; graph search must preserve improved routes and reopen expanded states when needed.

That argument — f is a safe underestimate, so expanding in order of smallest f can never skip an optimal answer — is the heart of A*’s standard tree-search optimality guarantee. It requires some supporting conditions we should state honestly:

  • finite branching factor;
  • edge costs that are positive and bounded below (so cheap detours cannot hide a better route indefinitely);
  • and goal testing performed at selection, not generation (the same subtlety we met with uniform-cost search).

A final, important mindset point: admissibility is a mathematical property of the estimate — it is never established by “it worked on a few examples.” Just because A* found good answers in practice does not prove the heuristic was admissible. To claim optimality you must verify h really cannot overestimate for all states, through reasoning about the problem (e.g., the relaxation argument from earlier), not anecdote.

Chapter 12 / 22Consistency checks each edge

Admissibility is the property you need for A*’s optimality, but there is a second, stronger condition called consistency (also known as monotonicity) that makes many guarantees cleaner and simpler. Let us see what it demands.

for every edge u → v with cost c(u,v):   h(u) ≤ c(u,v) + h(v)
  • Read in words: the estimate at u must be no larger than “pay for this one move, then finish from v.” In other words, the heuristic should not estimate a greater remaining cost here than the cost of one move plus the estimate at its successor — a condition that looks just like the triangle inequality you may know from geometry.
  • Intuitively: my guess of remaining distance from u should not exceed (the cost to get to v) plus (my guess from v). If it did, h would be “optimistic in a way that contradicts its own neighboring estimates.”

The practical payoff of consistency is beautifully simple:

consistency → f = g + h is nondecreasing along any path
  • As A* extends a path, its f value never drops. That monotonicity means the first time a state is selected/expanded it already has its final best cost — no later surprises force revisiting.
  • It also implies admissibility: with h(goal)=0, consistency guarantees h never overestimates anywhere (you can chain the inequality down to a goal). So consistent ⇒ admissible; but the reverse does not hold.

The lecture’s running tree gives you a crisp example of the gap between them: an admissible yet inconsistent heuristic. Suppose h(A)=5, while the edge cost from A to B is c(A,B) and h(B) makes c(A,B)+h(B)=3. Then:

h(A)=5  >  c(A,B)+h(B)=3 → admissible overall, but VIOLATES consistency on this edge
  • It is still admissible (it never overestimates the true cost to a goal), yet inconsistent — it fails the per-edge triangle inequality. Such heuristics are possible and perfectly safe for optimality in tree search.

Why does this distinction matter so much? Because of graph search that closes states. When an algorithm records “state X is fully expanded, discard it,” a consistent heuristic lets us safely never revisit X (since its selected path already had the best possible g). An inconsistent-but-admissible heuristic may require the ability to reopen closed states when an improved route arrives with lower cost — more bookkeeping and potentially more work. So knowing which property your heuristic has tells you exactly how much care graph search must take.

Chapter 13 / 22Graph search must keep better routes alive

When searching a graph (as opposed to a tree), two paths that end at the same state are not necessarily equivalent — and this section explains why careful bookkeeping matters. The key observation is simple:

two routes reaching identical state X ≠ equal: they may have very different accumulated costs g
  • Imagine arriving at city X once having spent 10, and again having spent only 4. The second route is strictly better — it reaches the same situation cheaper.
  • A good graph search therefore should retain the best known cost for each state. When a newly discovered route reaches an already-seen state at lower g, we update that record (or “reopen” the state if it was closed) so the improved path is not lost.

The precise bookkeeping depends on the algorithm and its assumptions:

  • With a consistent heuristic, f never decreases along paths, so the first time we expand a state its g is already final — closing it permanently is safe (this is why consistency simplifies graph search).
  • With an inconsistent but admissible heuristic, f can dip later. If you close a state too early and refuse ever to revisit it, you may throw away the record of a genuinely cheaper route discovered afterwards — losing the optimal solution entirely.
inconsistent h + permanent close-too-early → optimal path can be missed

This is precisely why we spent time distinguishing consistency from admissibility: it directly determines whether a graph search must support reopening closed states or can safely discard them forever.

A separate warning about negative edge costs, because they break the whole framework we have built:

  • All of our reasoning assumed costs are nonnegative. A negative edge can make an expensive partial path become cheaper later. Endless decrease requires a reachable negative cycle that can still lead to a goal.
  • The classic pathological case: if there is a reachable cycle with total negative cost somewhere on the way to the goal, then you can loop around it repeatedly and reduce your total without bound. In that situation the “optimum” is not just hard to find — it does not exist as a finite number; the best value is unbounded (−∞).

The lesson: negative edges require entirely different algorithms and reasoning (this is beyond our scope, but good to recognize why we assume nonnegativity everywhere here). For all of A*’s guarantees, hold onto that assumption — it is load-bearing.

The bound test as a mathematical algorithm

For every v ∈ V:   0 ≤ h(v) ≤ h*(v)
Explore p only if g(p) + h(end(p)) < B.

h*(v) is the actual least cost from v to a goal. Nonnegativity and admissibility imply h(goal) = 0. With nonnegative edge costs, f(p) = g(p) + h(end(p)) is a lower bound on any solution extending p. B is an upper bound supplied by the best complete solution already found; initially use B = ∞ with no saved solution.

F ← stack(⟨vₛ⟩); B ← ∞; best ← none
while F ≠ ∅:
    p ← pop(F)
    if g(p) + h(end(p)) ≥ B: continue
    if end(p) = vG:
        best ← p; B ← g(p)
    else:
        for v with (end(p), v) ∈ E:
            if v is not in p: push(F, p ⊕ v)
return best

How to read the code: pop selects the latest stack entry. If its lower bound is at least B, continue skips directly to the next loop iteration. Otherwise a goal updates both the saved route and B; a non-goal generates legal extensions p ⊕ v. Checking that v is not already in p prevents cycles on that route without a global visited set that might discard a cheaper alternative. With nonnegative costs, a cycle is not needed to obtain one optimum. Only an empty stack triggers the final return.

This version terminates on a finite graph because only finitely many simple paths exist. On infinite spaces, termination requires further conditions, discussed below. Branch-and-bound is a powerful idea for finding provably optimal solutions when A*’s frontier would require too much memory. Safe pruning still requires a lower bound; with nonnegative costs, h = 0 is valid when no more informative heuristic is available. The name captures its two-part strategy: branch by exploring alternatives depth-first, and bound by pruning away anything that cannot beat the best solution found so far.

  • The algorithm retains the incumbent, the best complete solution found so far, and uses its cost as the upper bound. Before any solution is found, the bound may be set to infinity.
  • As search proceeds depth-first, whenever we reach a goal and finish a route, we compare its cost with the incumbent and update if better — so the incumbent improves over time.

The pruning step is what gives branch-and-bound its efficiency:

if lower bound on finishing this partial path ≥ current incumbent → PRUNE (skip it)
  • For any partially explored path, we can compute a lower bound: the cost spent so far plus an underestimate of what remains. If even that best-case total is no better than (or equal to) our incumbent — if it cannot possibly improve on the solution already in hand — then there is no point continuing down this branch. We cut it off immediately and avoid generating its descendants.

Here is a key mental shift from plain search: finding one complete solution does not necessarily end branch-and-bound; instead, it tightens the search. A cheaper incumbent lowers B, so more partial paths meet f ≥ B and can be pruned. Only when every remaining possibility has been explored or pruned do we know our current incumbent is optimal.

solution found → incumbent updated → bound tightens → more pruning → continue until all candidates resolved

Because a strong early incumbent lets us prune aggressively, good neighbor ordering matters enormously: if depth-first happens to find an excellent solution quickly (by trying promising branches first), the cost bound becomes low early and many later branches can be eliminated safely. Poor ordering finds only mediocre solutions late, pruning little.

A precise clarification separates two different claims that students often blur:

  • Optimality on completion: if branch-and-bound terminates with an incumbent, is it guaranteed to be optimal? Yes — provided every pruned branch was really bounded below correctly (never overestimated), so nothing better was discarded.
  • Termination itself: will the algorithm always finish and return that optimum? This is a separate question. With an initial infinite bound, plain depth-first could chase an infinite branch forever without ever finding any incumbent — never getting the chance to prune. To guarantee termination you need the search space actually explored to be finite (e.g., a finite graph with cycle pruning), or additional assumptions (bounded costs/depths) for infinite spaces.

So: optimality-on-completion and termination are independent guarantees, each requiring its own conditions — keep them separate when you reason about the algorithm.

Chapter 16 / 22The frontier rule explains the algorithm

The comparison table in this section offers one of the most useful perspectives for understanding — and even reading — search algorithms: summarize each method by its frontier rule, i.e., “exactly how does it decide which candidate to take next?” Organizing them that way reveals a clean taxonomy:

  • Queue methods (breadth-first) and stack methods (depth-first): selection depends purely on insertion order — oldest first, or newest first. No scalar score; just the data structure’s discipline.
  • Scalar-priority methods: each candidate carries a number used to rank it against all others.
    • Uniform-cost: priority = g (cost spent so far).
    • Greedy best-first: priority = h (remaining estimate only).
    • A*: priority = f = g + h (both together).
  • Branch-and-bound: combines depth-first traversal with an incumbent-based rejection test — it explores deep like DFS but refuses to continue any partial path whose lower bound cannot beat the best complete solution so far.
frontier rule = what ranks candidates + when you discard them

This framing is not just tidy — it is genuinely practical. When you encounter a new or unfamiliar search implementation, ask yourself four questions and the algorithm’s behavior will fall out:

  1. What does it store? Paths in a queue/stack? Scored candidates in a priority structure?
  2. How does it rank candidates? By age, depth, g, h, f, or some combination?
  3. When does it check for the goal? On generation or on selection (as we saw matters so much for optimality)?
  4. What information allows it to discard a route? Pruning by bound? Closing visited states? Cycle detection?

The answers to those four questions determine everything about the algorithm’s completeness, optimality and efficiency — far more than memorizing which name goes with which behavior. Once you can describe any search method in terms of its frontier rule and these four decisions, you truly understand it.

Chapter 17 / 22Choose from the problem’s requirements

With the whole toolkit now on the table, how do you pick? The answer should always start from what your problem requires, not from what algorithm you happen to like. Work through requirements in this order:

  1. Minimum number of steps (equal edge costs)?
    • If memory is plentiful → breadth-first search: fewest edges, simple.
    • If memory is tight → iterative deepening: same fewest-edge guarantee at stack-sized memory, with repeated work whose size depends on branching, depth and where the goal is found.
  2. Minimum weighted cost (edges differ, all nonnegative)?
    • No useful heuristic available → uniform-cost search, the honest uninformed choice.
    • A suitable admissible estimate exists that could cut exploration dramatically → consider A*: it preserves optimality when its conditions and duplicate policy are sound; the benefit depends on heuristic quality, evaluation cost, ties and reopening.
  3. Optimization needed but a large best-first frontier impractical? → branch-and-bound, which searches depth-first (tiny memory) and prunes using an incumbent, trading a smaller frontier for depth-first exploration; storage still depends on depth, and termination must be checked.
objective + resource constraints → candidate algorithm(s)

A few practical reminders that keep the choice honest:

  • “Memory permits” and “tight” are real engineering judgments, not abstractions — a huge branching factor can make even one BFS layer infeasible.
  • The guarantee you expect is only as good as its assumptions being met: A* optimality needs admissibility, nonnegative costs, goal testing on selection and sound duplicate handling, including reopening when needed. UCS also needs correct graph duplicates. Eventual completion has separate cost and branching assumptions. If an implementation skips those, the promised property silently vanishes.

In other words, algorithm selection is a matching problem — map your objective (steps vs. weighted cost vs. any solution) and your constraints (memory, availability of a heuristic, admissibility you can verify) onto the method whose guarantees fit. Implementation details still determine which guarantees actually apply, so always double-check that the code honors its assumptions.

Chapter 20 / 22Search is controlled exploration

The deepest way to understand everything in this lecture — both parts of it — is a single phrase: search is controlled exploration. Left alone, your problem is an enormous (often astronomically large) collection of possibilities. Search transforms that chaos into an orderly, methodical investigation by imposing structure at every level:

  • A sound representation defines legal states and actions. We decide what counts as a situation worth tracking and which moves are permitted — this is the map on which all exploration happens. Get it wrong and everything downstream inherits the error.
  • The frontier records unfinished paths. Rather than juggling every possibility at once, we keep only those candidates not yet fully explored, organized so they can be selected sensibly.
  • A selection rule decides where effort goes next. This single choice — oldest, newest, cheapest-so-far, best-estimated-completion — determines the algorithm’s entire personality and guarantees.

Two accelerators refine this control:

  • Heuristics (informed methods) steer effort toward promising regions using cheap estimates of what remains;
  • Pruning (as in branch-and-bound, or closing visited states) discards whole branches that cannot possibly matter.

Admissibility protects the completion lower bounds used by A* and branch-and-bound. Consistency lets graph A* close a state after its best path is selected, with sound duplicate handling. Greedy and heuristic DFS can use the same admissible estimate yet still lack a minimum-cost guarantee. Always distinguish the estimate’s property from the selection rule and the implementation policy.

control = representation + frontier + selection rule · efficiency boosters (heuristics, pruning) must stay valid

This leads to the central habit of the whole course on search — a reflex worth practicing constantly:

Every claimed property — speed, completeness, optimality, memory use — must be traceable back to the specific rule and assumptions that produce it.
  • If someone says “this method is complete,” ask: under which conditions? (finite branching? bounded depth?)
  • “Optimal”? Under what heuristic or cost assumptions?
  • “Uses little memory”? Which data structure, and how are paths stored?

Anchor every property in its mechanism and you will never be fooled by a name — the single most transferable skill from this entire lecture.
